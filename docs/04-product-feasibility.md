## 分类标准

| 类别 | 含义 |
|---|---|
| ① 直接支持 | 现有 MCP 工具即可完成 |
| ② 间接支持 | 需要本地算法、状态存储或普通工程逻辑配合 |
| ③ 存在依赖 | 需要额外授权、调度服务、通知渠道或外部组件 |
| ④ 暂不支持 / 无法确认 | 无足够依据，或实测证明无此能力 |

## 一、功能 A：预算随机餐品盲盒

### A1 · 获取真实且适用于当前门店的价格

**判定：① 直接支持 ✅（原为 ④，实测后升级）**

- ✅ `query-meals` 直接返回 `currentPrice`（现价）与 `originalPrice`（原价），单位元
- ✅ 实测与 `calculate-price` 结果完全吻合（麦香鸡 17 + 可乐 9.5 = 26.5，两边一致）
- 🎯 **这是本轮最大的好消息**：盲盒可**完全离线枚举组合**，不再需要逐个调 `calculate-price` 试探，`calculate-price` 只用于最终校验

⚠️ **但有一个价格陷阱必须处理**：
`canWithOrder=true` 且 `discountType="随单购麦金卡优惠"` 的商品，其 `currentPrice` 是**必须同时随单购会员卡才能拿到的价格**。
实测：`龙焰鸡腿堡四件套 currentPrice=29 / originalPrice=57`。
→ **默认应排除这类商品，或单独标注"需随单购麦金卡"**。否则会报出用户到店拿不到的价格，直接摧毁产品可信度。

### A2 · 计算优惠后的实际应付金额

**判定：① 直接支持 ✅**

- ✅ `calculate-price` 实测可用，返回 `originalPrice` / `discount` / `price`
- ✅ **确认无副作用**：同参重复调用结果一致，不产生订单/购物车 → 可放心批量调用
- ⚠️ 金额单位为**分**（菜单为元），需 ÷100

### A3 · 确定优惠券是否可叠加

**判定：④ 暂不支持 → 实测已否决 ❌**

- ❌ 实测返回 `{"code":600022,"message":"暂不支持多张券使用"}`
- 🎯 **官方明确：一个订单只能用 1 张券**
- 产品设计调整：
  - **"优惠优先"模式 = 对每张可用券分别算一次，取实付最低的那个**，而不是叠加
  - 绝不向用户承诺"叠加最优"

### A4 · 在预算范围内生成多个有效候选组合

**判定：② 间接支持 ✅（前提已满足）**

- 菜单 + 价格已齐备，组合生成本地即可完成，无需 MCP 参与
- `calculate-price` 仅用于最终 N 个候选的校验（N 建议 ≤ 5）
- 🎯 **新增利器**：`query-meal-detail` 的 `diffPrice` 可为负（实测小杯玉米杯 `-¥0.5`），
  → 预算差一点时可用"换子项降价"把总价压进预算，这是比"换一个组合"更优雅的解法

### A5 · 不创建真实订单的情况下验证价格

**判定：① 直接支持 ✅（U3 已通过）**

- ✅ 实测：同参重复调用 `calculate-price` 两次，返回完全一致，**未产生任何订单或购物车**
- ✅ 批量试算安全，可放心用于多候选比价

### A6 · 获取足够商品信息处理忌口和过敏原

**判定：④ 暂不支持（过敏原）＋ ② 间接支持（忌口粗粒度）**

- ❌ **过敏原**：`list-nutrition-foods` 实测 160 条，字段仅 `energyKj/energyKcal/protein/fat/carbohydrate/sodium/calcium`，**确认无过敏原、无配料成分**
- ✅ **忌口可做三层降级**：
  - L1 分类排除：`query-meals.categories[].name`（13 个分类）
  - L2 标签排除：`tags` 含「川香风味」「韩式风味」「辣」等（实测存在）
  - L3 名称关键词：本地匹配
  - L4 套餐子项替换：用 `query-meal-detail` 把套餐里的辣味小食换成别的（**实测可行**）
- ⚠️ 营养数据名称与菜单不完全一致（全半角括号差异），需做名称归一化

> **红线**：必须声明"忌口过滤基于分类与名称关键词，不能替代官方过敏原信息"，这同时满足赛事合规要求。

### A7 · 随机结果避免重复与无效组合

**判定：② 间接支持 ✅**

- 纯本地：组合指纹（商品编码排序拼接）+ 会话内集合去重
- 无效过滤：预算外、`canWithOrder` 商品、售罄项在生成阶段剔除

### 功能 A 汇总

| 子功能 | 初版判定 | **实测判定** | 说明 |
|---|---|---|---|
| A1 真实价格 | ④ | **① ✅** | `query-meals` 带价格 |
| A2 优惠后实付 | ② | **① ✅** | `calculate-price` |
| A3 券叠加 | ④ | **④ ❌ 已否决** | `600022` |
| A4 多候选生成 | ② | **② ✅** | 本地算法 + 换子项降价 |
| A5 无订单验证价格 | ② | **① ✅** | 无副作用已确认 |
| A6 忌口/过敏原 | ④ | **④ 过敏原 ❌ / ② 忌口 ✅** | 三层降级 |
| A7 去重 | ② | **② ✅** | 本地 |

**🎯 功能 A 结论：核心链路完全成立，且比预期更简单。唯一必须小心的是 `canWithOrder` 价格陷阱。**

## 二、功能 B：限定活动与优惠助手

### B1 · 是否存在可靠的官方活动查询接口

**判定：① 直接支持（工具存在）＋ ⚠️ 结构化程度不足**

- ✅ `campaign-calendar` 实测可用，返回当月全部活动，按日期分组（往期/今日/未来）
- ❌ **无结构化起止日期字段** —— 日期只是分组标签
- ⚠️ 但文案内嵌价格锚点（`15.9元起`、`26.9元起`、`29.9元`…），有实际价值
- ✅ `specifiedDate` 入参可精确查某一天

### B2 · 区分全国 / 地区 / 门店 / 用户专属活动

**判定：④ 暂不支持 → 实测已否决 ❌**

- ❌ 实测无任何适用范围字段
- ✅ **替代方案已验证可行**：不做范围分层，改做**数据源分层**
  - 「活动日历」= 公开营销活动（`campaign-calendar`）
  - 「我的券」= 用户专属权益（`query-my-coupons`，14 张）
  - 「可领券」= 待领取（`available-coupons`）
  - 三者天然区分了公开 vs 个人，比强行分层更准确

### B3 · 查询活动有效期及适用条件

**判定：活动 ④ ❌ ／ 优惠券 ① ✅**

- ❌ **活动**：无结构化日期字段，倒计时不可靠
- ✅ **优惠券**：完全支持
  - `query-store-coupons.tradeDateTime`：`2026-10-05 10:30:00-2026-10-09 23:59:59`
  - `query-my-coupons.有效期`：精确到日期 + 时段 + 星期，且有 **「今日到期」标签**
  - `query-store-coupons.products[]`：**适用商品 productCode**，可判断是否配得上当前餐品

> 🎯 **重要方向调整**：到期提醒应建立在**优惠券**上而不是活动上——券有精确有效期和现成的「今日到期」标签，活动没有。

### B4 · 检测活动数据变化

**判定：③ 存在依赖**

- ❌ MCP 侧确认无任何订阅/推送/变化检测能力
- ✅ 可行路径：本地快照 + diff（对活动标题、券列表做集合比对）

### B5 · WorkBuddy 是否具备定时任务及通知机制

**判定：③ 存在依赖**

- ✅ WorkBuddy 提供 `automation_update`，支持 `recurring`（RRULE）/ `once`，以及 `validFrom`/`validUntil`
- ⚠️ 属宿主侧能力，Skill 无法自带调度；是否按时唤醒取决于客户端是否运行
- ⚠️ 是否有系统级推送通知需实测确认

### B6 · 若宿主不支持后台运行的替代方案

**判定：② 间接支持 ✅（推荐作为主方案）**

- 用户主动问"有什么新活动/我的券"时，读本地快照 → 拉取 → diff → 输出 🆕 新增 / ⏳ 今日到期 / 🔄 仍在
- 零后台依赖、零额外授权
- 定时 automation 作为**可选增强**，由用户自行创建

### B7 · 订单创建与用户确认流程【第二轮修订】

**判定：② 间接支持 ✅（原为 ③）** —— 升级理由：`create-order` 入参与 `calculate-price` 高度同构，工程复杂度远低于初版预估。

**已确认（Schema + 官方描述）**

| 项 | 结论 |
|---|---|
| 工具存在性 | ✅ `create-order`（官方：返回订单详情与支付链接） |
| 必填参数 | `storeCode`、`orderType`、`beType`；场景附加 `takeWayCode`（orderType=1）、`addressId`（orderType=2）、`items[]` |
| `takeWayCode` 来源 | ✅ **实测确认**取自 `calculate-price.takeWayList[].code`（实测 `locker-out`） |
| 与算价的参数关系 | ✅ **入参高度同构**，算价请求体可复用为下单骨架，仅补 `takeWayCode` |
| 套餐子项替换 | ✅ 通过 `items[].roundList[].comboItemList[].code`（配合 `query-meal-detail.diffPrice`） |
| 优惠券传入 | ✅ `items[].couponId` + `couponCode`，与算价一致；**一单限 1 张**（`600022`） |
| 取餐方式 | ✅ `takeWayCode` 即取餐方式（实测"外带 · 店外取餐柜"） |
| **支付时限** | ✅ **15 分钟**（实测 `expirePayTime` − `createTime`） |
| 支付由谁完成 | ✅ **用户自行支付** —— MCP 侧无任何支付工具（支付能力不在 30+ 工具清单内），架构上不可能自动付款 |

**仍未验证（需实测或用户授权）**

| 项 | 状态 |
|---|---|
| 支付链接字段名与形态 | ❓ 未知（`query-order` 无 payUrl 字段，官方描述有"支付链接"） |
| 能否在浏览器打开 / 跳微信小程序 | ❓ 未知，官方文档从未提及小程序 |
| 用户是否需重新登录 | ❓ 未知 |
| 未支付订单超时后状态 | ❓ 未知（15 分钟时限已知，超时结果未知） |
| 未支付订单是否占用优惠券 | ❓ 未知 |
| `cancel-order` 是否归还券 | ❓ 未知 |

**判定说明**：核心链路（选品 → 算价 → 确认 → 创建 → 用户自付）**完全成立**；缺口集中在"支付链接的呈现方式"与"未支付订单的善后"，属于**体验细节而非可行性阻塞**。

### B8 · 一键领券（`auto-bind-coupons`）

**判定：② 间接支持（可行）＋ ⚠️ 存在未验证风险**

| 子项 | 判定 | 依据 |
|---|---|---|
| 能否"一键领全部" | ✅ **直接支持** | 官方明确"自动领取…所有券"，无需指定 couponId |
| 能否单张领 | ❌ **不支持** | 全量工具中无单券领取接口 |
| 领取前能否展示清单 | ✅ **直接支持** | `available-coupons` 返回券名 + 状态（已领取/可领取） |
| 领取后能否核对结果 | ✅ **直接支持** | 再调 `available-coupons` / `query-my-coupons` 比对 |
| 影响面是否可控 | 🟢 **实测仅 3 张可领** | P-16 |
| 是否消耗积分 | 🟡 **倾向不会，未证实** | 积分消耗在 `mall-create-order`/`draw-lottery`；已记录基线 |
| 是否会领到付费权益 | 🟡 **低风险** | 可领券中含"9.9元中杯冰美式"（到店付费使用），但领取免费 |
| 重复调用行为 | ❓ **未知** | — |
| 部分失败的返回结构 | ❓ **未知** | — |

**结论：可以纳入 MVP，但必须满足三条前置条件**

1. 领前必须先展示 `available-coupons` 清单
2. 必须明确告知"这是**批量领取全部可领券**，不能只领其中一张"
3. 领取后必须再查一次券池并如实汇报（不得预先承诺张数）

> 若实测发现会消耗积分、领到付费权益或存在不可逆副作用，则**降级为"只展示清单 + 给出官方领券入口"**。

### B9 · 忌口范围收窄（产品决策）

**判定：② 间接支持 ✅（范围收窄后风险显著下降）**

- ✅ 只做：不喜欢的餐品/食材（名称与分类黑名单）、是否吃辣（标签 + 关键词）
- ❌ 不做：过敏原识别系统、不承诺过敏安全
- 依据：`list-nutrition-foods` 确认**无过敏原/配料字段**（U8），技术上无法支撑
- 收窄后的好处：不再需要维护过敏原词表，也不必承担"漏判导致过敏"的责任风险

|---|---|---|---|
| B1 官方活动查询 | ① | **① ⚠️** | 可用但仅文本，无结构化日期 |
| B2 活动分层 | ④ | **④ ❌** | 改用数据源分层 |
| B3 活动有效期 | ④ | **❌ 活动 ／ ✅ 券** | 券有精确有效期+今日到期标签 |
| B4 变化检测 | ③ | **③** | 本地快照 diff |
| B5 WorkBuddy 定时通知 | ③ | **③** | automation 存在，宿主依赖 |
| B6 主动触发比对 | ② | **② ✅** | 主方案 |

**🎯 功能 B 结论：把重心从"活动"移到"券"。券的数据质量远高于活动——有有效期、有到期标签、有适用商品、有 couponId 能直接算价。活动只能做展示层。**

| **G6** | `create-order` 返回是否含可用支付链接（字段名/形态） | ✅ **已通过**（2026-10-11 首次真实下单） | 返回 `https://m.mcd.cn/mcp/scanToPay?orderId=...`；浏览器可直开 → 扫码 → 跳麦当劳 App |

| **G8** | `auto-bind-coupons` 是否消耗积分 / 领到付费权益 | ❓ **未验证**（已记录积分基线 145，可领前后比对） | 降级为"只展示可领清单 + 官方入口"，不自动领 |
| **G9** | 支付链接能否在浏览器打开 / 是否需重新登录 | ✅ **已通过**（用户亲测） | 浏览器可直开（扫码画面）；App 未登录过需登录、登录过免登录；**不扫码也可在 App / 微信小程序里找到订单** |

> ⚠️ **G7 仍未验证**，不得当作已知事实。
> 15 分钟支付期限为**本单服务端 `expirePayTime` 实际值**，不是全局常数。

### 3.3 最终结论

- ✅ **功能 A 可以完整实现，且实现难度低于预期** —— 这是本次参赛的主力功能
- ✅ **功能 B 的"券"部分可以高质量实现**（到期提醒、适用商品匹配、算价）
- ✅ **下单闭环（选品 → 算价 → 确认 → 创建 → 用户自付）可以完整实现**，且因入参与算价同构，成本低于预期（B7 由 ③ 升级为 ②）
- ✅ **一键领券可以纳入**，当前影响面仅 3 张券，风险可控（B8）
- ⚠️ **功能 B 的"活动"部分只能做展示层**，不能做倒计时/范围过滤
- ❌ **精确过敏原过滤明确不做**（忌口收窄为简单偏好过滤）
- ❌ **券叠加明确不支持**
- ❌ **自动付款明确不做** —— MCP 侧不存在支付工具，架构上不可能
- ⚠️ **"提醒"必须降级为用户主动触发**或依赖 WorkBuddy automation（可选增强）

### 3.4 推荐 MVP（第二轮修订版 —— 已移除"不接下单、不领券"）

> 🔄 本轮按产品决策变更修订。旧版 MVP 的「不接下单、不自动领券」结论**已作废**。

** MVP 三条主线（共享同一条「选品 → 算价 → 确认 → 创建订单」流水线）**

1. **预算盲盒**
   菜单带价 → 本地组合 → 排除 `canWithOrder` → 忌口/偏好过滤 → Top 3 → `calculate-price` 精算 → 展示实付与节省 → 可换一批
2. **羊毛雷达**
   `query-my-coupons`（含今日到期）+ `query-store-coupons`（能算价）+ `available-coupons`（可领清单）+ `campaign-calendar`（今日/未来活动）→ 快照 diff
3. **确认与下单闸门（MVP 必做）**
   明确选品 → `calculate-price` 实时校验 → 展示最终订单摘要 → **用户明确确认** → `create-order` → 返回支付入口 → **用户自行付款**
   ＋ **一键领券（MVP 纳入）**：展示可领券 → 用户明确同意 → `auto-bind-coupons` → 复查券池 → 汇报结果

**MVP 工具集（11 个）**
`now-time-info`、`query-nearby-stores`、`query-meals`、`query-meal-detail`、`calculate-price`、`query-my-coupons`、`query-store-coupons`、`available-coupons`、`campaign-calendar`、`create-order`、`auto-bind-coupons`
（可选：`order-list` / `query-order` 用于下单后核对；`cancel-order` 用于取消）

**验收标准**

| # | 标准 |
|---|---|
| 1 | 给一个预算，10 秒内返回**真实金额**、可复现、可换一批的组合 |
| 2 | 一句话列出今日到期券与当前可领券 |
| 3 | 说出"下单"后，**必须**经过完整摘要复述 + 明确确认才调用 `create-order` |
| 4 | 未收到明确确认时，**绝不**调用 `create-order` / `auto-bind-coupons` |
| 5 | 确认后**不得**再更换商品、门店或优惠券 |
| 6 | 下单成功后展示支付入口 + **15 分钟支付时限**，并说明需用户自行完成支付 |
| 7 | 领券前必须展示清单并说明"批量领取全部"，领券后如实汇报结果 |
