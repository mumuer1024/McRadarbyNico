| # | 初稿假设 | 实测结果 | 影响章节 |
|---|---|---|---|
| C1 | 担心 `query-meals` 无价格，需批量 `calculate-price` 试探 | ✅ **菜单直接带价**，可离线枚举，`calculate-price` 只做最终校验 | 第 7 节算法大幅简化 |

| C5 | 券字段未知 | ✅ `query-store-coupons` 有 couponId + 有效期 + **适用商品 productCode**；`query-my-coupons` 有**「今日到期」标签** | 到期提醒与优惠匹配可高质量实现 |
| C6 | 未预见到价格陷阱 | 🆕 **`canWithOrder` 商品价格绑定随单购会员卡**，不买卡拿不到 | 必须默认排除或标注 |

### 第二轮新增校正（C7–C10）

| # | 旧假设 | 实测 / 审计结果 | 影响 |
|---|---|---|---|
| C7 | `create-order` 参数复杂、实现成本高 | ✅ **入参 ≈ `calculate-price` 入参 + `takeWayCode`**，算价请求体可直接复用 | 下单模块开发量大幅下降 → 可安全纳入 MVP |
| C8 | 未支付订单可能长期挂账、占券 | ✅ **支付时限 15 分钟**（`expirePayTime` − `createTime` 实测）；是否占券仍未知 | 可做支付倒计时；占券问题需用保守话术 |
| C9 | 一键领券风险过高、影响面大 | 🟢 **当前仅 3 张可领**；消耗积分的是另外两个工具（`mall-create-order` / `draw-lottery`） | 风险显著低于预期 → 可纳入 MVP（待实测确认） |
| C10 | 订单状态可用数字码判断 | ❌ **实测 `status:"40"`，与官方注释枚举（1/2/4/6/7/8/10）不符** | 状态判断只能用 `orderStatus` 中文文本 |

**新增的隐藏王牌**：`query-meal-detail` 的 `diffPrice` **可为负**（实测小杯玉米杯 `-¥0.5`）→ 预算差一点时可用"换套餐子项降价"压进预算。

**第二轮新增的两条硬约束**

- 🔒 **MCP 侧不存在任何支付工具**（30+ 工具清单中无支付能力）→ 「用户自行付款」不是产品选择，而是**架构必然**
- 🔒 **`auto-bind-coupons` 是批量接口**，全量工具中**没有单张领券接口** → 确认话术必须说清"会领取全部可领券"

## 1. 核心定位与目标用户

**一句话定位：**
> 一个用真实麦当劳数据帮你做「今天吃什么」和「有什么羊毛」决策的 WorkBuddy Skill —— **输入预算，抽一个真的能下单的组合；问一句，拿到当前可用的全部优惠与活动。**

**目标用户（按优先级）：**

1. **麦当劳高频消费者**（学生、上班族）：每天纠结吃什么，追求性价比，愿意为"少花 5 块"花 10 秒
2. **价格敏感型用户**：关注麦麦省、优惠券、活动日历，但懒得逐个翻 App
3. **麦当劳 MCP 开发者 / 参赛者**（次要）：把这个 Skill 当作 MCP 能力组合的参考实现

**不服务的场景：** 营养处方、减肥计划、过敏原精确规避、代客自动下单。

## 2. 两项功能如何共享数据与业务逻辑

这是本方案的核心设计——**A 和 B 不是两个功能，而是同一份「事实层」上的两种消费方式**。

```
                    ┌─────────────────────────┐
                    │  共享事实层（MCP 只读）  │
                    ├─────────────────────────┤
                    │ · 门店上下文（nearby/   │
                    │   delivery-stores）     │
                    │ · 菜单快照 query-meals  │
                    │ · 我的券 query-my-coupons│
                    │ · 门店券 query-store-…  │
                    │ · 可领券 available-…    │
                    │ · 活动日历 campaign-…   │
                    │ · 时间基准 now-time-info│
                    └───────────┬─────────────┘
                                │
              ┌─────────────────┴─────────────────┐
              │                                   │
    ┌─────────▼──────────┐            ┌───────────▼──────────┐
    │  功能 A 预算盲盒    │            │  功能 B 活动优惠助手  │
    ├────────────────────┤            ├──────────────────────┤
    │ 菜单 + 券 + 预算    │            │ 活动 + 券 + 快照 diff │
    │   ↓ 本地组合算法    │            │   ↓ 本地快照比对      │
    │ 候选集              │            │ 🆕 新增 / ⏳ 将结束   │
    │   ↓ calculate-price│            │   ↓                  │
    │ 实付金额 + 节省     │            │ 快捷下单入口          │
    └─────────┬──────────┘            └───────────┬──────────┘
              │                                   │
              └───────────────┬───────────────────┘
                              │
                    ┌─────────▼──────────┐
                    │  统一确认与下单闸门  │
                    │ create-order（双确认）│
                    └────────────────────┘
```

**共享点具体化为三条：**

| 共享资产 | 被 A 使用 | 被 B 使用 |
|---|---|---|
| **门店上下文**（首次询问后缓存） | 决定菜单与价格 | 决定门店券与适用范围 |
| **券池**（我的券 + 门店券 + 可领券） | 参与价格计算 | 作为"我的羊毛"清单展示 |
| **价格裁决器**（`calculate-price` 封装） | 盲盒实付金额 | 活动商品下单前的最终确认 |
| **下单闸门**（双确认 + 金额复述） | 抽中后下单 | 看中活动后下单 |

## 3. 用户典型使用场景

**场景 1 · 午饭纠结（最高频）**
> "我只有 30 块，不想吃辣，帮我抽一个麦当劳午餐"
> → 抽到：麦香鱼 + 中薯 + 中可，实付 ¥28.5，用券省 ¥4.5
> → "换一个" → 抽到第二组

**场景 2 · 极端预算**
> "身上就 15 块，能吃什么"
> → 明确告知：最低组合 ¥12，给出 3 个候选；若 15 元确实组不出套餐，诚实说明而不是编造

**场景 3 · 优惠盘点**
> "我现在有哪些券能用？有没有快过期的"
> → 列出券池 + 有效期 + 建议搭配

**场景 4 · 活动发现**
> "最近麦当劳有什么活动？有什么新品？"
> → 活动日历（进行中/即将开始）+ 与上次查询对比的 diff

**场景 5 · 从抽中到下单（MVP 主线）**
> "就这个，下单"
> → 复述门店/商品明细/原价/优惠/实付/将使用的券 → 用户确认 → `create-order` → 返回支付入口 + 15 分钟时限
> → **用户自己打开麦当劳 App 或扫码付款**，Skill 不代付

**场景 6 · 从活动到下单（功能 B 汇入同一闸门）**
> "那个 9.9 冰美式我要了"
> → 与场景 5 **完全相同的**算价 → 确认 → 下单流程

**场景 7 · 一键领券（MVP 纳入）**
> "把能领的券都领了"
> → 展示 `available-coupons` 清单（当前 3 张）→ 明确说明"将批量领取全部可领券" → 用户确认
> → `auto-bind-coupons` → 再查一次券池 → 汇报"新到手 X 张，仍可领 Y 张"

**场景 8 · 长期复购（长期版）**
> "还是昨天那单"
> → 读历史订单 `order-list` 复现

## 4. 关键交互流程

### 4.1 首次使用（一次性引导）

```
用户首次调用
  → 询问默认城市/位置（可选，可跳过用"最近常用门店"）
  → query-nearby-stores / delivery-query-stores
  → 让用户选一个默认门店（或选"每次问我"）
  → 缓存到 skill 本地配置（非 MCP 侧，不写敏感信息）
  → 询问忌口（可跳过）：分类黑名单 + 关键词
```

### 4.2 预算盲盒主流程

```
① 解析用户输入 → {预算, 时段, 忌口, 偏好, 模式}
② 加载共享事实层（菜单 + 券池，带 TTL 缓存）
③ 本地过滤：品类黑名单 → 关键词忌口 → 偏好加权
④ 本地组合：按模式生成候选
      - 完全随机：均匀采样
      - 优惠优先：优先含可用券的组合
      - 饱腹优先：优先主食+小食+饮料的完整组合
⑤ 去重：排除本次会话已抽中过的组合指纹
⑥ 取 Top N（建议 3-5）送 calculate-price 精算
⑦ 选出主推 1 个 + 备选 N-1 个
⑧ 渲染输出：明细 / 原价 / 优惠 / 实付 / 节省 / 剩余预算
⑨ 等待用户："换一个" → 回 ④（排除已抽中）｜"就这个" → 进入下单闸门
```

### 4.3 活动优惠助手主流程

```
① 解析意图 → {查活动 / 查我的券 / 查可领券 / 关注某商品}
② 并行拉取：campaign-calendar + query-my-coupons + available-coupons
③ 读取本地上次快照（首次则无）
④ diff：🆕 新增活动 / ⏳ 即将结束 / 🔄 仍在进行 / ❌ 已下线
⑤ 分类渲染：活动日历 / 我的券（含有效期）/ 可领券
⑥ 写入本次快照
⑦ 可选：用户可创建 WorkBuddy 定时 automation 做定期检查（引导而非强制）
⑧ 若用户要买 → 进入下单闸门
```

### 4.4 统一成交流水线（A / B 共用，MVP 核心）

> 按本轮决策：功能 A 与功能 B **不再各自为政**，而是在选品之后汇入同一条流水线。

```
        功能 A 预算盲盒                    功能 B 活动优惠助手
        （抽中一个组合）                  （看中一个活动/券商品）
                │                                  │
                └──────────────┬───────────────────┘
                               ▼
                     ① 明确选品（商品 + 数量 + 套餐子项 + 特调）
                               ▼
                     ② calculate-price 实时校验
                        · 取 takeWayList[].code → takeWayCode
                        · 若用券：逐券试算取实付最低（一单限 1 张）
                        · 得到实付 / 优惠 / 节省（单位：分 → 元）
                               ▼
                     ②b 【算价覆盖核对】verify_pricing_covers_items
                         🔴 开发期实测发现：请求 {麦香鸡, 可乐中杯}，服务端
                            productList 只回了麦香鸡、总价也只算麦香鸡 ——
                            商品被**静默丢弃**且不报错。缺任何一件都必须拦截，
                            重新拉菜单重来，绝不让用户为"少了东西"的订单付款。
                               ▼
                     ③ 渲染【最终订单摘要】
                        门店 / 就餐方式 / 取餐方式 / 商品明细
                        原价 / 优惠 / 实付 / 将使用的券 / 数据时间
                               ▼
                     ④ 用户【明确确认】
                               ▼
                     ⑤ create-order
                               ▼
                     ⑥ 返回支付入口 + 15 分钟支付时限
                               ▼
                     ⑦ 用户自行付款（Skill 不参与、不代付）
                               ▼
                     ⑧ 用户回"支付完成/失败" → query-order 查最新状态
```

### 4.5 下单闸门（双重确认细则）

```
触发条件：用户明确表达购买意图（"下单""买了""就这个""我要了"）
  ↓
【闸门 1 · 信息复述】必须完整展示：
   · 门店名称 + 就餐方式（到店自取/得来速/麦乐送/团餐）
   · 商品明细（含套餐子项与特调）
   · 原价 / 优惠 / 实付金额（元）
   · 将使用的优惠券名称（若有）
   · 数据获取时间
  ↓ 等待用户明确回复"确认"（"好""行""嗯""OK" 不算）
【闸门 2 · 风险告知】必须明确说明：
   · 将创建真实订单，占用所选优惠券
   · 需在 15 分钟内完成支付，超时订单将失效
   · 支付需由你本人完成（本 Skill 不会、也无法代付）
   · 可回复"取消"随时中止
  ↓ 等待用户明确回复"确认下单"
调用 create-order（一次性，失败不自动重试）
  ↓
返回支付入口 + 订单号 + 15 分钟倒计时
```

> 原则 1：**任何含糊表达都不得被视为下单确认**。
> 原则 2：**确认之后严禁再变更商品、门店或优惠券**；若用户要求改动，必须回到闸门 1 重新走一遍。
> 原则 3：**`create-order` 失败或超时绝不自动重试**（可能造成重复单）；先查 `order-list` 确认是否已创建成功，再由用户决定是否重来。

### 4.6 领券闸门（一键领券细则）

```
触发条件：用户明确要求领券（"把能领的都领了""一键领券"）
  ↓
① 调 available-coupons，展示可领取清单（实测当前 3 张）
  ↓
② 【明确告知】这是"批量领取全部可领券"，
   MCP 不提供单张领取接口，无法只领其中某一张
  ↓ 等待用户明确回复"确认领取"
③ 调 auto-bind-coupons
  ↓
④ 再调 available-coupons / query-my-coupons 复查
  ↓
⑤ 如实汇报：新到手 X 张 / 仍可领 Y 张 / 失败 Z 张
   （不得预先承诺张数；以复查结果为准）
```

> ⛔ 未收到明确同意前，绝不调用 `auto-bind-coupons`。
> ⛔ 绝不把批量领取描述为"帮你领这一张"。
> ⚠️ 若实测（G8）发现会消耗积分或领到付费权益 → 立即降级为"只展示清单 + 官方入口"。

## 7. 随机组合算法基本思路

**不追求最优解，追求"合理 + 快 + 不重复"。**

### 7.1 数据结构

```
商品 = { code, name, category, tags[], price?, nutrition? }
约束 = { budget, excludeCategories[], excludeKeywords[], requireCategories[] }
组合 = { items[], 指纹 = sort(itemCodes).join("|") }
```

### 7.2 生成流程（实测后简化版）

```
0. 取菜单：query-meals 已自带 currentPrice（元），无需价格探测
   ⚠️ 默认剔除 canWithOrder=true 的商品（价格绑定随单购会员卡）
      —— 或单独归为"加购麦金卡可享"分组，明确标注

1. 过滤：剔除黑名单品类（categories[].name）与关键词忌口 → 候选池 P
   标签层过滤：tags 含「川香风味」「韩式风味」等辣味标签

2. 分类分桶：主食 / 小食 / 饮料 / 甜品 / 早餐

3. 组合模板（保证"像一顿饭"而不是随机堆砌）：
   - 完整餐：主食 ×1 + 小食 ×1 + 饮料 ×1
   - 简餐：主食 ×1 + 饮料 ×1
   - 单点：主食 ×1
   - 加餐：小食 ×1 + 饮料 ×1

4. 按模式加权采样：
   - 完全随机：各模板等概率
   - 优惠优先：优先选命中"我的券"适用商品的主食
   - 饱腹优先：优先完整餐模板 + 高热量主食

5. 预算筛选（本地精确计算，菜单已带价，无需估算）：
   保留 total ∈ [budget*0.6, budget] 的候选

6. 排序（本地启发式）：越接近预算且组合越完整，得分越高

7. 取 Top N（3-5）→ 送 calculate-price 精算（单位：分，÷100）→ 得到真实实付
   ⚠️ calculate-price 已确认无副作用，可安全批量调用

8. 最终过滤：实付 ≤ budget，否则：
   a) 丢弃；或
   b) 【超预算救场】对套餐类商品调 query-meal-detail，
      找出 diffPrice 为负的子项替换（实测玉米杯 -¥0.5），压进预算
   c) 仍不行则标记"略超预算 ¥X"，由用户决定

9. 抽取：从精算通过的组合中随机选 1 个作为主推
   记录指纹到 session 已抽集合，重抽时排除
```

### 7.2.1 三种模式（实测后修正）

| 模式 | 实现方式 | 实测依据 |
|---|---|---|
| 完全随机 | 各模板等概率采样 | — |
| **优惠优先** | ① 取 `query-store-coupons.products[].productCode` 得到"能用券的餐品"；② 优先把这些餐品放进组合；③ **对每张可用券各算一次 `calculate-price`，取实付最低** | ❌ 券不可叠加（`600022`），故只能"选最优单券"而非叠加 |
| 饱腹优先 | 优先完整餐模板 + 主食优先 | — |

### 7.3 去重与防无效

- **会话内去重**：指纹集合，重抽排除
- **无效处理**：售罄/不可售商品在菜单阶段剔除；`calculate-price` 报错的组合直接丢弃并记录原因
- **兜底**：若预算过小组不出任何组合，明确输出"这个预算当前门店组不出套餐，最低为 ¥X"，**绝不编造**

### 7.4 为什么不做穷举最优

- 菜单规模 × 组合模板会产生上万组合，逐个 `calculate-price` 会撞限流且体验慢
- 用户要的是"一个还不错的、能立刻下单的选择"，不是"数学最优解"
- 控制复杂度，符合"不为功能数量扩大工程规模"的约束

## 8. 优惠与价格真实性的保障方案

| 措施 | 说明 |
|---|---|
| **唯一权威源** | 所有展示给用户的金额，必须来自 `calculate-price` 的返回，**禁止本地估算值直接展示** |
| **单位统一** | `query-meals` 返回**元**（字符串），`calculate-price` 返回**分**（整数）；封装层必须统一换算，否则会差 100 倍 |
| **排除随单购陷阱** | `canWithOrder=true` 的商品其 `currentPrice` 需随单购会员卡才成立；默认排除，或强制标注"需随单购麦金卡，否则 ¥XX（原价）" |
| **券不叠加** | 官方 `600022`：一单一券。绝不展示"叠加后价"，只对每张券单独算价取最优 |
| **区分标注** | 本地估算只在内部排序用；对外输出只展示服务端返回的实付/优惠/节省 |
| **缓存 TTL** | 菜单缓存 30 分钟，券池缓存 10 分钟，活动缓存 6 小时；超时强制刷新 |
| **失败即降级** | 任何 MCP 调用失败 → 不猜测、不编造，明确告知用户"获取失败，请重试" |
| **时间戳标注** | 输出中附带"数据获取时间"，让用户知道信息新鲜度 |
| **免责声明** | 固定尾注：价格/库存/优惠以麦当劳官方渠道实时结果为准 |
| **对账机制** | 下单前**必须**重新调用 `calculate-price` 校验一次，防止缓存过期导致金额偏差 |

> 这条是产品的信任基础：**宁可少展示，不可错展示。**

## 9. 安全边界与用户确认机制

### 9.1 三级操作分级

| 级别 | 操作 | 工具 | 确认要求 |
|---|---|---|---|
| 🟢 安全 | 查菜单、查活动、查券、算价格 | `query-*`、`calculate-price`、`campaign-calendar` | 无需确认，直接执行 |
| 🟡 敏感 | 读取个人账户数据（我的券、积分、地址） | `query-my-coupons`、`query-my-account`、`delivery-query-addresses` | **首次**询问授权；结果脱敏展示 |
| 🔴 危险 | 领券、下单、取消、抽奖、兑换、改地址 | `auto-bind-coupons`、`create-order`、`cancel-order`、`draw-lottery`、`mall-create-order`、`delivery-create-address` | **必须双重显式确认 + 完整信息复述** |

### 9.2 硬约束（第二轮修订）

- ❌ **绝不在未收到明确确认时调用 `create-order`**（哪怕用户已说过"下单"，也必须走完 4.5 双闸门）
- ❌ **绝不在未收到明确同意时调用 `auto-bind-coupons`**（哪怕用户说"帮我薅羊毛"）
- ❌ **绝不自动付款** —— MCP 侧不存在支付工具，架构上也不可能
- ❌ **绝不在确认后更换商品 / 门店 / 优惠券**；改动必须回到闸门 1
- ❌ **绝不自动重试 `create-order`**（失败/超时先查 `order-list` 确认状态）
- ❌ **绝不把批量领券描述为单张领取**
- ❌ **绝不承诺过敏安全**（忌口仅基于分类与名称关键词）
- ❌ 绝不在未复述金额的情况下下单
- ❌ 绝不存储用户真实地址、手机号、会员 ID 的明文
- ❌ 绝不在日志/文档/仓库中写入 Token
- ❌ 绝不绕过任何 MCP 报错继续尝试
- ✅ 所有危险操作默认提供"只给我方案，我自己下单"的退出选项
- ✅ 领券与下单的全部结果都必须**如实汇报**，包括失败与部分失败

### 9.2b 写操作台账（开发时必须逐条实现）

| 写操作 | 前置 | 防重 | 事后 |
|---|---|---|---|
| `create-order` | 闸门 1 复述 + 闸门 2 风险告知 + 明确确认 | 指纹（门店+场景+商品排序+券）+ 时间窗；失败不重试 | 展示支付入口 + 15 分钟时限；`order-list` 核对 |
| `auto-bind-coupons` | 展示 `available-coupons` 清单 + 说明批量 + 明确同意 | 同一会话内重复请求需再次确认 | 复查券池，如实汇报 |
| `cancel-order` | 用户明确要求 + 复述订单号与原因 | — | 提示"订单已取消" |
| `draw-lottery` | ❌ **不实现**（消耗积分） | — | — |
| `mall-create-order` | ❌ **不实现**（消耗积分） | — | — |
| `delivery-create-address` | ❌ **MVP 不实现**（改账户数据） | — | — |

### 9.3 敏感数据脱敏规则

- 地址：只显示"XX区XX路"，门牌号与收件人脱敏
- 券码：不展示完整券码，只展示券名与面额
- 订单号：可展示（用于查询），但不落盘
